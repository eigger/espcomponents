# AI 에이전트용 UARTEx 패킷 구성 지침

[기본 지침서(English)](PACKET_GUIDE.md) · [한국어 플랫폼별 설정 예제](README.ko.md#플랫폼별-설정-예제)

장치 설명서나 캡처를 받아 ESPHome YAML을 작성할 때 사용한다. 작업 중인 버전의 [공통 스키마](__init__.py)와 해당 플랫폼의 스키마(예: [스위치](switch/__init__.py))에서 사용할 키와 값 형식을 확인한다. [한국어 사용 안내](README.ko.md) · [영문 레퍼런스](README.md)

## 적용 기준과 근거

이 지침의 UARTEx 기준은 2026-11-21에 확인한 espcomponents 커밋 `e3b1d72`이다. 3절의 가상 프로토콜 예제는 해당 컴포넌트와 ESPHome `2026.11.0`에서 `esphome config`로 검증했다. [기준 커밋의 UARTEx 소스](https://github.com/eigger/espcomponents/tree/e3b1d72680e30377b1ddc3c4fa3116beb0a968a0/components/uartex)

- **설정 문법과 동작**은 사용자가 실제로 빌드하는 `external_components`의 태그·커밋 또는 로컬 소스를 기준으로 판단한다. 공통·플랫폼별 Python 스키마에서 키·형식·기본값을 확인하고, 패킷 비교·체크섬·재시도는 같은 버전의 C++ 구현과 대조한다.
- **장치별 바이트의 의미**는 대상 모델의 프로토콜 명세와 방향·조작이 기록된 캡처를 근거로 정한다. 둘이 어긋나면 해당 필드를 미확정으로 표시하고 모델·펌웨어와 추가 캡처를 확인한다.
- **결과를 전달할 때**는 사용한 UARTEx 리비전, ESPHome 버전, 검증 범위(설정 검사·빌드·실기기 송수신 중 수행한 항목)를 기록한다.

## 1. 캡처에서 확인할 것

- 캡처의 출처, 장치 모델, UART 속도·패리티·정지 비트, 캡처가 전체 프레임인지 이미 분리한 페이로드인지 기록한다.
- 각 프레임에 ESP 기준 방향(RX/TX), 조작, 관측 시각, 실제 상태를 붙인다. 켜기와 끄기, 다른 채널 조작, 유휴 시의 주기적 보고를 비교해 주소·명령·상태 바이트를 구분한다.
- 명령 직후 수신한 프레임은 응답 후보다. 송신 에코나 주기적 상태 보고일 수 있으므로 요청과 응답의 대응을 확인한 경우에만 `ack`를 설정한다. 상태 보고만 확보했다면 수신 엔티티부터 작성하고 송신을 확정하는 데 필요한 캡처를 명시한다.

## 2. 프레임 경계와 체크섬 결정

전선상의 순서는 `헤더 | 페이로드 | 체크섬 | 푸터`다. 장치에서 실제 사용하는 부분만 설정한다. RX와 TX 형식은 각각 확인한다.

| 캡처에서 확인한 규칙 | 설정에 옮기는 방법 |
|---|---|
| 전체 길이가 일정함 | `rx_length`에 프레임의 전체 바이트 수를 쓴다. |
| 길이 필드가 있음 | `rx_data_length`에서 전체 길이 = 헤더 길이 + offset + 길이 필드 폭 + 필드 값 + adjust + 체크섬 길이 + 푸터 길이. 길이가 다른 캡처에도 같은 식을 적용한다. |
| 명령 종류에 따라 전체 길이가 달라짐 | `rx_length` 람다에서 헤더를 포함한 누적 바이트를 보고 전체 길이를 반환한다. 접근하려는 바이트가 아직 없으면 0을 반환한다. |
| 고정 종료 바이트가 있음 | `rx_footer`에 지정한다. 페이로드 안에도 같은 바이트열이 보이면 길이 등 실제 경계 조건을 함께 확인한다. |
| 체크섬이 있음 | 값이 다른 프레임 여러 개에서 계산 범위와 결과를 대조한다. 예를 들어 `add`는 헤더와 페이로드의 합에서 하위 1바이트를 취하고, `add_no_header`는 페이로드만 더한다. |

## 3. 바이트를 YAML에 대응시키기

다음은 설명용 가상 프로토콜이다. 첫 두 바이트는 헤더, 마지막 두 바이트는 푸터다. 같은 채널에서 상태 보고, 제어 명령, ACK의 첫 페이로드 바이트가 각각 다르다.

| 방향과 의미 | 헤더 | 페이로드 | add | 푸터 |
|---|---|---|---|---|
| RX 켜짐 보고 | 02 01 | 10 03 01 | 17 | 0D 0A |
| RX 꺼짐 보고 | 02 01 | 10 03 00 | 16 | 0D 0A |
| TX 켜기 | 02 01 | 20 03 01 | 27 | 0D 0A |
| RX 켜기 ACK | 02 01 | 30 03 01 | 37 | 0D 0A |
| TX 끄기 | 02 01 | 20 03 00 | 26 | 0D 0A |
| RX 끄기 ACK | 02 01 | 30 03 00 | 36 | 0D 0A |

아래 설정은 기존 `uart:` 버스 하나에 연결한다. 예를 들어 켜짐 보고의 체크섬은 16진수로 `02 + 01 + 10 + 03 + 01 = 17`이다.

```yaml
uartex:
  rx_header: [0x02, 0x01]
  tx_header: [0x02, 0x01]
  rx_footer: [0x0D, 0x0A]
  tx_footer: [0x0D, 0x0A]
  rx_checksum: add
  tx_checksum: add

switch:
  - platform: uartex
    name: "채널 3"
    state: [0x10, 0x03]
    state_on: {offset: 2, data: [0x01]}
    state_off: {offset: 2, data: [0x00]}
    command_on:
      data: [0x20, 0x03, 0x01]
      ack: [0x30, 0x03, 0x01]
    command_off:
      data: [0x20, 0x03, 0x00]
      ack: [0x30, 0x03, 0x00]
```

- `state`가 보고 종류와 채널을 먼저 확인한다. `offset: 2`는 원래 페이로드의 세 번째 바이트다. 같은 채널의 ACK(`30 03 01`)는 `10 03` 필터를 통과하지 않는다.
- 상태의 `mask`는 해당 `offset`부터 수신값에 AND 연산을 적용한다. 예를 들어 `{offset: 2, mask: [0x0F], data: [0x01]}`은 수신값 `0xA1`과 일치한다. 명령의 `mask`는 ACK 페이로드의 첫 바이트부터 적용한다.
- 숫자는 `offset`, `length`, `signed`, `endian`, `precision` 순으로 실제 표본값에 대조한다. 예를 들어 `FF 9C`를 2바이트 big-endian 부호 있는 정수로 읽으면 −100이고, `precision: 1`이면 −10.0이다.
- 바이트열은 `[0x10, 0x03]`로 쓴다. 문자열은 문자 데이터로 해석되므로 `"10 03"`은 공백을 포함한 다섯 문자다.
- 한 명령이 여러 채널 값을 덮어쓰는 장치는 다른 채널의 RX/TX 위치가 같을 때 엔티티의 `state`와 명령의 `preserve_state`를 검토한다. 갱신된 상태 보고가 있어야 다음 보존 명령을 보낼 수 있다. [코콤 조명 예제](../../packages/wallpad/kocom/fragments/light.yaml)

## 장치별 패킷 판독 사례

아래 값은 저장소 프리셋에서 계산한 검증용 입력이다. 대상 장치의 실측값과 대조해 적용한다.

| 장치 | 수신 판독과 송신 검증 |
|---|---|
| CVNet 난방 1 | 보고 접두사는 `20 01 4A`다. 오프셋 4가 `98`, 5가 `16`이면 난방 중, 목표 24°C, 현재 22°C다. 오프셋 4의 최상위 비트가 난방 모드, 하위 7비트가 목표값이다. 난방과 25°C를 함께 요청하면 명령의 온도 바이트는 `99`가 되어야 한다. |
| CVNet 환기팬 | 보고 접두사 `20 01 71`에서 오프셋 4가 전원, 6이 풍량이다. 전원 01과 풍량 03은 켜짐·3단이다. 속도 명령에는 단계를 넣고 ACK 접두사 `20 01 71 91`를 확인한다. |
| CVNet 가스 밸브 | 열림·닫힘은 모두 보고하지만 프리셋이 정의하는 송신은 닫기다. 열림 보고로부터 열기 명령을 추정하지 않는다. |
| 블라인드·오디오 | 장치가 퍼센트 바이트를 쓸 때 수신 `32`는 50%이므로 두 플랫폼 모두 0.50을 게시한다. 송신 람다의 50% 인수는 블라인드 위치 0.50, 오디오 볼륨 50이다. 각각 전선상 `32`로 되돌아가는지 확인한다. |

[CVNet 프리셋](../../packages/wallpad/cvnet/cvnet.yaml) · [플랫폼 선택과 검증 절차(영문)](PACKET_GUIDE.md)

## 4. 결과 검증과 전달

1. 캡처별로 예상 동작을 적고 YAML과 대조한다. 위 예에서는 `10 03 01`만 켜짐, `10 03 00`은 꺼짐이며 `10 04 01`(다른 채널)과 `10 03 02`(정의되지 않은 값)는 상태를 유지해야 한다.
2. 각 명령에 TX 헤더·체크섬·푸터를 적용해 전선상의 바이트열을 복원하고 원본 송신 캡처와 대조한다. ACK는 해당 명령의 수신 페이로드와 별도로 비교한다.
3. 보드와 UART 설정이 포함된 최종 파일에 `esphome config <파일.yaml>`을 실행한다. 고정 길이 프레임의 범위를 벗어난 필드, 마스크로 만들 수 없는 예상값 등의 경고도 확인한다. 사용자 람다를 작성했다면 `len`이 충분한지 검사하고 `esphome compile <파일.yaml>`로 빌드한다.
4. 사용자에게 YAML, 바이트 위치표, 캡처별 예상 결과, 수행한 검증을 함께 전달한다. 아직 확인할 수 없는 필드에는 필요한 표본을 명시한다. 예를 들어 채널 주소를 확정하려면 다른 채널에서 같은 조작을 한 캡처가 필요하다.
